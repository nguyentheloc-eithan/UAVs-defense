C-UAS Vision Platform

An object-oriented, enterprise architecture for detecting, tracking and classifying small drones from video, fused with radar and RF. Use both languages: C++ for the real-time runtime, Python for everything that trains, evaluates and operates around it.

01 · Decision

C++ or Python?

Hybrid, with a hard boundary. The always-on pipeline (capture, decode, inference, tracking, fusion, alerting) is C++20. Model training, dataset tooling, evaluation, simulation and dashboards are Python. They meet at three artifacts: a TensorRT/ONNX model file, a protobuf schema, and a YAML config. Python never sits in the frame loop.

Data, labeling, evaluation, MLOps Poor Fits Richest ecosystem
Operator tools, APIs, dashboards Possible Fits FastAPI, plotting, quick UIs

  • Decode, preprocess, tiling
  • Detector inference (TensorRT)
  • Tracker, fusion, threat scoring
  • Alert and C2 gateway, recorder

Python — lifecycle

  • Dataset curation and labeling

  • Simulation and synthetic data
  • Ops dashboard and reporting API

Prototype shortcut: run phase 1 entirely in Python on recorded video to get a baseline fast. Then port only the frame loop to C++ behind the same interfaces.

02 · System

Enterprise architecture

Hexagonal (ports and adapters) core. Every external thing, whether a camera, radar, model runtime or C2 system, sits behind an interface, so the core logic runs identically against live sensors, recorded files or simulators.

Deployment

Edge node (per site)

Jetson Orin or x86 + RTX. Runs the full runtime so a site keeps detecting if the network drops. Docker, read-only root, signed images.

Command node

Aggregates tracks from many edge nodes into one air picture. Hosts operator UI, evidence store, config and model registry.

Training environment

Separate, GPU cluster, Python. Produces versioned model artifacts that edge nodes pull and verify by signature.

03 · Classes

OOP design

The pipeline depends on four narrow interfaces and nothing concrete. Swapping a detector, adding a radar or changing the alert channel is a new class plus one line in the factory, with no edits to the core.

Patterns and why each is there

Pattern Where What it buys
Strategy IDetector, ITracker, IThreatPolicy Swap algorithms per site or A/B test models with a config change
Adapter Sensor sources Vendor protocols stay out of the core; one mock per interface for tests
Decorator TiledDetector wraps any detector Small-object tiling added without touching model code
Abstract factory + registry ComponentRegistry Plugins register by name; config picks them at start
Observer / pub-sub Event bus Recorder, UI and C2 listen to the same tracks independently
State Track lifecycle Confirmation and loss rules live in one place, tested in isolation
Command PTZ slew-to-cue Operator and automatic cues share one auditable path

05 · Domain

What makes drone detection hard

Tiny targets

A small quadcopter at range is a few to a few dozen pixels. Use tiled inference over full-resolution frames, a stride-4 detection head, long focal length, and train on crops that match the real pixel sizes.

Birds and clutter

Birds, insects, kites and aircraft cause false alarms. Add a second-stage classifier on the track crop, and score motion over time (wingbeat, flight path), not single frames.

Day, night, weather

Pair visible with thermal. Keep one model per modality or a fused-input model, and gate each by image quality metrics.

Moving platform

PTZ and vehicle-mounted cameras move. Estimate ego-motion so the tracker works in world coordinates, and the motion detector subtracts camera movement.

Sensor fusion

Radar gives range and velocity but poor classification; video gives class but no range. Fuse tracks on bearing and time, then confirm hostile class only with video or RF evidence.

Metrics that matter

  • Probability of detection by range band
  • False alarms per camera-hour
  • Time from first visible to confirmed track
  • Track continuity (ID switches)

Human on the loop. The platform detects, tracks, classifies and alerts. Any effector or response is a separate system, gated by an operator decision, and every alert carries its evidence clip and the track history that produced it.

07 · Plan

Roadmap

Durations are indicative for a team of 4–6 and move with data availability.

Phase 02–3 weeks

Requirements and data

Concept of operations, threat list, required detection ranges, false-alarm limits, legal and export review. Collect or acquire drone, bird and background footage from the real sensors.

Exit: signed requirements and a labeled seed dataset.

Phase 1~6 weeks

Python baseline

Train a baseline detector and tracker on recorded video. Build the replay and evaluation harness. Define the protobuf contracts.

Exit: Pd and false-alarm numbers per range band, on a frozen test set.

Phase 28–10 weeks

C++ core runtime

Interfaces, pipeline, video adapter, TensorRT detector with tiling, tracker, event bus. Match phase 1 accuracy and meet the latency budget.

Exit: one live stream, end-to-end under budget, replay regression green.

Phase 36–8 weeks

Fusion and C2

Radar and RF adapters, fusion engine, PTZ cueing, threat policy, alert gateway, operator UI, evidence recorder.

Exit: multi-sensor site demo with operator workflow.

Phase 4~6 weeks

Hardening and field trials

Hardware-in-the-loop tests, soak tests of 7 days or more, security review, failure injection (lost sensor, GPU reset, network cut), live drone trials in varied weather.

Exit: acceptance against phase 0 requirements.

Phase 5ongoing

Operate and improve

Collect hard cases from the field, retrain, ship signed models through the registry, track drift in false-alarm rate.

08 · Risk

Main risks

Risk Impact Mitigation
Too little real drone footage at long range High Early field collection, synthetic data for augmentation only, test set always from real sensors
False alarms from birds erode operator trust High Second-stage classifier, temporal scoring, per-site threshold tuning, report false alarms per hour from day one
Model accuracy drops after a change Medium Frozen replay set gating CI, model registry with rollback
Vendor lock-in on GPU or camera SDK Medium All vendor code behind adapters; ONNX kept as the portable model format
C++ team ramp-up Medium Keep the C++ surface small (the frame loop), enforce sanitizers and clang-tidy, Python for all other work
Regulatory and export limits Medium Review in phase 0, keep model and data handling auditable
